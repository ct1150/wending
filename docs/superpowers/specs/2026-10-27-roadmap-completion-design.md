# 问鼎 4.0：不同出身、完整仙途与免费剧情创作

## 用户目标与实施判断

用户要求将审计中的剩余待办同步到 Git，并按顺序完成。既有授权包括开发、测试、合并及现有 Cloudflare 游戏发布。用户已多次要求按推荐直接推进，本轮不重复开启发现访谈。以下具体数据、模块划分及发布方案属于实施者选择，不冒称用户逐项指定。

主要目标是能玩的修仙文字肉鸽：玩家知道自己是谁、为何求仙、正在争取什么；每次选择影响资源、关系、机缘和未来；各世拥有不同开局及中后段冲突。药谷和药的主题退出新默认故事中心。

## 方案选择

1. 直接扩写旧 CV1/CV2：改动表面小，但容易改变旧随机序列、开局和存档验证；PR #11 已暴露这种风险。
2. 新增完全独立存档 v5：隔离清晰，但须改动多个现有应用和迁移边界。
3. **采用 v4 / contentVersion 3，独立规则模块，经现有导出分发。** 旧 CV1/CV2 模块冻结，保持现有 UI 和存档入口；只有新的推荐开局采用 CV3。

## 全局约束

- 原生 JavaScript、Node.js >=22、零浏览器运行时依赖；浏览器模块只使用相对路径的静态具名 import/export。
- 存档仍使用 `baishi-wending-save-v1`；保留 v1/v2/v3 和 v4 CV1/CV2 的规则、随机序列、导入导出及旧人生。
- 新存档 envelope 仍是 version 4、mode cultivation、contentVersion 3；旧记录不自动升级。
- 所有动作验证 revision 与 sceneId；失败不扣费、不推进时间或随机状态；读取、刷新和查看抽屉不抽随机。
- 完整历史不静默截断，继续使用 1,000,000 JavaScript 字符的存档边界。
- 选项通常 2–3 个；缺条件、伤势、折寿与确定死亡需选择前可见；数值细节放人物抽屉。
- 游戏和离线包不携模型 API key，不要求玩家联网调用模型。

## 开局

首批四种常规出身为 `village` 山村猎户、`artisan` 城坊匠徒、`ferry` 渡口短工、`exile` 流亡孤儿。各自有不同目标、人物关系、至少三段专属开场和两种有效策略。额外的 `wanderer` 前尘行者通过真实幽冥经历解锁。

每次掷骰产生根骨/悟性/气运，总和恰为 12，各项 1–6，以及两项不同命格。可锁定当前一项命格后重掷；锁定和结果持久化，入世后不能重掷。出身可从已解锁列表选择，选择也保存。

命格为 `keen-memory` 过目成诵、`sensitive-breath` 听息敏锐、`iron-bones` 坚韧筋骨、`sword-bone` 天生剑骨、`flash-wisdom` 刹那慧心、`fortune-debt` 福祸相依、`rootless` 无灵根异相、`void-echo` 前尘回响。前六项初始可得，后两项由实际经历解锁。每项有可见优势和代价，至少一个前十次行动内可遇到的专属机会；组合另有真实条件与效果，不以改名代替玩法。

前世仅携一项已得法门；特殊出身/命格的解锁来自已记载的世界成就，死亡次数不直接发奖。

## 故事与成长

新增模块位于 `src/game/cultivation/v3/`。主线按人间入门、宗门/散修立足、秘境/异兽/海域机缘、筑基、金丹、幽冥试炼、元婴、天界、化神、登仙、问鼎展开。各阶段有真实材料/修为/伤势/年月前置，不能靠一次交接直接升级。

境界及寿限：凡人 80、炼气 120、筑基 240、金丹 480、元婴 800、化神 1500、登仙 3000 年。这些只适用于新 CV3。境界必须逐级突破；突破动作至少耗 2/3/5/8/12/20 年，达到各自修为和物品前提；不能先借下一境界寿限来支付本次成本。

新主线至少 100 个有实际选择的可达场景（含分支，不把 3×3×3 排列当作 27 篇独立故事），正常完整问鼎路线至少 55 次选择；允许玩家选择提前归隐、承担危险或因寿尽失败。场景数量是覆盖门槛，不是可玩时长证明。核心场景有具体人物、目标、对话与行动后果，避免仅用摘要跳过中后期。

跨世保留关键人物/势力承诺、遗址变化、救援/背弃和三界成就。各世提前确定随机机缘，避免立刻重抽同一事件组合。世界后果需在后来的具体行动或可用路线中体现。

### 内容与规则接口

纯内容 `resolveCultivationScene(state)` 返回 `{id,title,location,goal,blocks,choices}`；段落继续使用 narration/dialogue，选项 `{id,label,detail,to,result,costs,effects,requires,ending?}`。内容不抽随机、不修改 state、不网络请求。规则与目录、条件、动作的确切接口由 Task 2 的契约文件固定，后续内容遵守。

公开接口保持 `createCultivation(options)`、`getCultivationView(state)`、`chooseCultivation(state,command)`、`validateCultivation(state)`；显式 `options.contentVersion === 3` 进入新规则，既有选项默认含义不变。

## 免费模型增强

采用可选离线创作工具：先从真实场景导出简报，调用本地 Ollama，得到只含文字的候选；严格校验、生成预览，再通过独立接受命令写入静态文字包。模型不能生成 executable code 或修改 costs/effects/requires/choice IDs。只为明确、可覆盖的静态文字位置生成；不能把状态相关文字改成虚假固定事实。

默认本地模型和端点可配置。支持 OpenAI-compatible 端点作为可选传输，但 key 只读环境变量；不内置公共免费额度承诺。拒绝无效 JSON、未知 ID、超长文字、重复键/条目、规则字段、失败或截断响应；保留已接受内容和可离线玩的作者原文。

真实模型调用与 fixture 测试分开记录；如果当前环境没有模型，不把模拟服务测试称作真实推理成功。

## 发布

保留原线上地址。先核实可用的 Cloudflare Builds/GitHub 授权；若连接缺失，采用无需额外密钥的公开静态发行通道：GitHub Actions 通过测试后将带来源 SHA 和 HTML SHA-256 的不可变发行包发布到专用分支，现有 Worker 校验并自动采用。Worker 缓存上一份有效包并内嵌基线，远端失败不能返回半份或损坏页面；health 返回实际服务的源码版本和摘要。自动内容发布和 Worker 程序本身的更新需明确区分。
