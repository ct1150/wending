# 云渡连续试航与接班

> 主代理按 superpowers:executing-plans 实施；所有子代理仅只读核验。

**目标：** 在已有三班云渡中增加有真实容量限制、接班条件与延续后果的试航。依据`docs/evidence/2026-11-18-campaign-pacing/README.md`，不将新增回合折算20小时。

**结构：** 新`cloud-trial.js`负责试航内容与校验；原`cloudPassage`的seat/route、修为、物品结算保持。`events.cloudTrials`仅记录明确接受之后的新行动。入口放在每班交割后的渡簿；未完试航在再次打开渡口时可继续，也能去原守候流程。

**技术：** 现有JavaScript规则事件、node:test、IndexedDB、Playwright离线包。没有AI调用或线上部署。

## 设计决定

- 每班是当下安排的一次试航或补验。先观察船位和岸上需求，再决定先接候渡者还是先带学徒。两组各需样船全部席位，不能同航兼顾。
- 先航用两日、一份行粮、两分灵力，只完成所选一组。随后亲自返航用两日、一份行粮；或安排岸上轮值/船上报声接续。先带学徒已练成接班；先接候渡者则需前班同法接班记录，或另花三日、四分灵力教班。该条件改变实际选项，不只是文字。
- 第一班用其已选渡法决定接班方式；第二、三班用第二班渡法。接续用三日、两分灵力。亲自返航不留下可供后班直接调用的轮值/报声班。
- 最后一班可以明确借用已经完成再访的风隙：定岩提供转乘落脚处，流槽提供空船引航。只有试航接受前已存在的通路可用，冻结在该班记录；不倒改旧航次。不去风隙也能完成全部试航。
- 可回山保留进度，或明确将尚未服务的一组交回常班并结束自己的试航。后者记录为交回，不冒充亲自完成双方；没有无限奖励或新增强制倒计时。
- 老玩家只补验当前最近已交割的一班，不假造过去三次首航。阶段递增，前一试航未结束不能另开；已结束阶段不可重复收费或领物。新内容不重复发雷印、丹药或修为。
- 新记录用`stage/start/marks/priority/sailed/trained/finished/method/refuge`。日期取实际结算，marks为两处观察，priority是两组之一，method为返航、岸班、报声、借隙或交回。严格验证次序、阶段和物资前置；死亡不写成功patch。
- 历史云渡场景精确匹配旧菜单后恢复原页，不放宽整场景或存档哈希校验。新菜单只在后续行动生成。

## 实际实现与验证

三班试航使用独立的`cloudTrials`记录。接班资格限定紧邻前班同法，跳过中间试航不能沿用较早记录；下一次接签至少比上次交割晚一日。下一班守候页也能翻船签；旧页仍保留原返回按钮。当前试航未结束时，渡口提供续行及原来的守候/风隙路线。
